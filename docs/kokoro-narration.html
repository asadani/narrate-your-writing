Why this one first

Most text-to-speech advice starts with a GPU. Kokoro doesn't need one. It renders slightly faster than real time on an ordinary laptop CPU, which changes what the tool is for: a re-render costs a coffee break, so you can fix a mispronunciation, change a pause, or rewrite a paragraph and just run it again.

The trade is that you get a voice, not your voice. If that is acceptable — and for most articles it is — this is the pipeline that gets you there with the least ceremony.

The pipeline

1

Install, and fetch two files

The runtime is a pip install. The model is two downloads that you keep beside your project rather than re-fetching:

pip install kokoro-onnx soundfile numpy

# kokoro-v1.0.onnx    325.5 MB   the model
# voices-v1.0.bin      28.2 MB   the voice style vectors

Pin the expected byte sizes in your fetch script and check them after download. A truncated model file fails deep inside the ONNX session with an error that tells you nothing useful.

2

Choose a voice — or blend one

This is the part most people miss. Kokoro's voices are style vectors, not separate models, which means they average. A blend is a real voice that no single preset gives you:

# an even mix of two British male voices
--voice bm_george+bm_fable

# or weighted, if you want one to dominate
--voice bf_emma*0.6+af_heart*0.4
blend = None
for name, weight in zip(names, weights):
    term = kokoro.get_voice_style(name) * (weight / total)
    blend = term if blend is None else np.add(blend, term)

Blending is worth the ten minutes. Single presets tend to have one distracting quality — a vowel, a cadence — that you stop being able to unhear at minute twenty. Averaging two voices sands that off.

3

Fix the acronyms before the model sees them

Kokoro's text frontend is espeak-based, and it will spell technical acronyms out letter by letter in ways that are wrong or simply ugly. You cannot fix this with prompting; you fix it with a substitution table applied to the text first.

SPOKEN_ACRONYMS = [
    (r"\bMCP\b",      "em see pee"),
    (r"\bJSON-RPC\b", "jayson arr pee see"),
    (r"\bJSON\b",     "jayson"),
    (r"\bAPI\b",      "ay pee eye"),
    (r"\bOAuth\b",    "oh-auth"),
    (r"\bHMAC\b",     "aitch-mack"),
    (r"\bstdio\b",    "standard eye-oh"),
]

Keep punctuation rules in a separate table from the phonetic spellings. The phonetic ones are specific to this engine and you will want to switch them off if you ever change models; the punctuation ones apply regardless:

SPOKEN_TYPOGRAPHY = [
    (r"\s*—\s*", ", "),      # em dash becomes a real clause pause
    (r"\s+([,.;:])", r"\1"),
    (r"\s+", " "),
]

Write numbers as words in the script itself

“JSON-RPC two point zero”, not “JSON-RPC 2.0”. Do it in the narration source rather than in a substitution rule — you will read the script aloud to check it, and you want to be reading what the model reads.

4

Structure by paragraph, and buy silence deliberately

Feed the model one paragraph at a time and insert the gaps yourself. Synthesised pauses are unreliable; concatenated silence is exact.

GAP_PARAGRAPH = 0.55   # between paragraphs
GAP_OPENING   = 0.85   # a longer beat after "Chapter nine."

for i, block in enumerate(blocks):
    samples, rate = kokoro.create(block, voice=voice,
                                  speed=args.speed, lang=lang)
    pieces.append(samples)
    if i < len(blocks) - 1:
        gap = GAP_OPENING if i == 0 else GAP_PARAGRAPH
        pieces.append(np.zeros(int(rate * gap), dtype=samples.dtype))

Those two constants do more for listenability than any parameter on the model. A slightly long pause reads as thinking; a slightly short one reads as rushing.

5

Slow it down

--speed 0.9   # ~170 wpm. Kokoro's 1.0 runs near 195.

195 words per minute is brisk for anything explanatory. 170 sits closer to a teaching pace, and listeners who want it faster have a speed control in their player — listeners who want it slower usually don't.

6

Normalise, then encode

Chapters rendered separately drift in loudness. Normalise each to the same peak so a listener isn't reaching for the volume between chapters:

audio = np.concatenate(pieces)
peak = float(np.max(np.abs(audio))) or 1.0
audio = (audio / peak) * 0.89        # even loudness across chapters

sf.write(mp3, audio, 24_000, format="MP3",
         bitrate_mode="VARIABLE", compression_level=0.4)

VBR at that setting lands around 1 MB per 2.5 minutes of speech — small enough to serve from a static site without thinking about it.

7

Hash the inputs so unchanged chapters skip

The single change that makes the pipeline pleasant to live with. Key a stamp on everything that affects output, and skip any chapter whose stamp is unchanged:

key = hashlib.sha256(
    ("\x00".join(blocks) + "|%s|%s|%s" % (voice, speed, lang)
     ).encode("utf-8")).hexdigest()[:16]

if not force and mp3.exists() and stamps.get(cid, {}).get("k") == key:
    print("%s  unchanged, skipping" % cid)
    continue

Fix a typo in chapter twelve and only chapter twelve re-renders. Write the stamp file after each chapter, not at the end of the run — otherwise an interrupted run loses every marker it earned.

ch04 took 53 minutes, and RAM is why

Not CPU — memory. On a machine with 8.5 GB total, one chapter hit a memory shortfall and spent 53 minutes on work its neighbours did in two and a half. Close the browser before a full run. If a chapter stalls disproportionately, it is paging, not thinking, and killing it and re-running costs less than waiting.

Two dead ends, so you can skip them

DirectML looks like free GPU acceleration. It isn't.

onnxruntime-directml advertises the provider, claims the node, and then dies inside Kokoro's F0 encoder on ConvTranspose with 80070057. Because it has claimed the node, there is no CPU fallback — nothing renders at all. And it installs over onnxruntime, so you have to uninstall one to try the other. Kokoro is fast enough on CPU that this is not worth chasing.

Make an explicit device request an assertion, not a preference

If --device cuda silently falls back to CPU, you will discover it an hour later. Let auto degrade quietly; make anything explicit fail loudly:

order = [p for p in wanted if p in have]
if not order:
    if device == "cuda":
        sys.exit("CUDA not available. Needs onnxruntime-gpu plus a driver "
                 "new enough for its CUDA version.")

Wiring it into a page

The last step is telling the article where its audio lives. Patch a manifest into the HTML rather than hand-maintaining a list — durations change every time you re-render, and a stale duration makes the player's scrubber lie.

/* AUDIO-MANIFEST:BEGIN */
{ "ch00": 128.4, "ch01": 125.0, "ch02": 157.7, ... }
/* AUDIO-MANIFEST:END */

Write it between sentinel comments and regenerate the block on every run. It costs ten lines and removes a whole category of silent breakage.

When to reach for something else

  • You want your own voice. Kokoro cannot do it at any setting — you need a cloning model. That is part two.
  • You need emotional range or per-line direction. Kokoro reads evenly and well; it does not act.
  • You need a language it doesn't cover. Check the voice list before committing to the pipeline.

For everything else — explanatory writing, documentation, courses, long-form articles — the economics are hard to argue with. 45 minutes of narration, 45 minutes of CPU, no GPU, no account, no per-character billing, Apache 2.0.
